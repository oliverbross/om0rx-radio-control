WHAT CHANGED?
=============
✅ OLD: Wavelog Log Modal used local MySQL database synced by wavelog_sync.py
❌ NEW: Wavelog Log Modal calls Wavelog API directly on-demand

WHY?
====
The old approach wasted API credits on continuous 1-minute sync loops
instead of calling the API only when the user opens the modal.

BENEFITS
========
✓ Always fresh data (instant from Wavelog, not 6+ minutes delayed)
✓ Fewer API calls (~99% reduction: 1440/day → ~50-100/day)
✓ No database maintenance needed
✓ Simpler architecture (fewer moving parts)
✓ Better performance (1-2 seconds vs 6+ minute latency)
✓ Lower API credit usage

HOW IT WORKS NOW
================
1. User opens "Wavelog Log" modal
2. Frontend calls: GET /api/wavelog/contacts?limit=100
3. Backend receives request
4. Backend calls Wavelog API: POST /api/get_contacts_adif
5. Backend receives ADIF string from Wavelog
6. Backend parses ADIF using _parse_adif_contacts()
7. Backend returns JSON to frontend
8. Frontend displays QSOs (no changes needed)

OLD vs NEW ENDPOINT BEHAVIOR
=============================
Before: GET /api/wavelog/contacts
  └─ Queries local MySQL database
  └─ Returns potentially stale data (6+ min old)
  └─ No 'source' field in response

After: GET /api/wavelog/contacts
  └─ Calls Wavelog API directly
  └─ Returns fresh data (instant)
  └─ Response includes 'source': 'wavelog_api'

TECHNICAL DETAILS
=================
Wavelog API Used: api/get_contacts_adif
Documentation: https://github.com/wavelog/wavelog/wiki/API#apiget_contacts_adif

Request to Wavelog:
  {
      "key": config.WAVELOG_API_KEY,
      "station_id": config.WAVELOG_STATION_ID,
      "fetchfromid": 0
  }

Response from Wavelog:
  {
      "exported_qsos": 100,
      "lastfetchedid": 4886,
      "message": "Export successful",
      "adif": "<call:5>N9EAT<qso_date:8>20240115..."
  }

ADIF Parsing:
  - Splits by <eor> (End Of Record) markers
  - Extracts fields using regex: <fieldname:length>value
  - Maps ADIF fields to frontend-expected dictionary keys
  - Respects the requested limit parameter

API CALL REDUCTION
==================
Before:
  ├─ Continuous: 1,440 calls/day (1 per minute)
  ├─ Database sync overhead
  ├─ Duplicate data storage
  └─ 6+ minute latency

After:
  ├─ On-demand: ~50-100 calls/day (estimated)
  ├─ No sync overhead
  ├─ No duplicate storage
  └─ ~1-2 second latency

Estimated savings: 93% reduction in API calls for this feature
